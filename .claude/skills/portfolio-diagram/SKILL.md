# /portfolio-diagram — 다이어그램 배치 다듬기

인자: `$ARGUMENTS` — 범위는 세 가지입니다.

| 입력 | 범위 | 하는 일 |
|---|---|---|
| `전체` | 모든 프로젝트의 모든 그림 | 프로젝트 순서대로, 그 안에서 문서 순서대로 다듬음(아래 「여러 그림을 한 번에」) |
| `<폴더>` (예: `2-Folk-Sack`) | 한 프로젝트의 모든 그림 | 그 기술 문서의 그림을 문서 순서대로 다듬음 |
| `<폴더> <절·번호·칸 글자>` (예: `3-Arcanist 3.3` · `3-Arcanist 5번` · `1-ODDITY "풀에서 대기"`) · 또는 그림 스크린샷 + 말 | 그림 하나 | 그 그림만 다듬음(요청이 있으면 그 요청대로) |
| 비어 있음 · `훑기 [폴더]` | 보기만 | 개선 후보를 우선순위 목록으로만(고치지 않음) |
| `준비` | — | 이 레포 렌더러에 다이어그램 엔진을 연결(처음 한 번, 아래 「준비」) |

`<폴더>`는 `src/` 아래 폴더 이름(앞부분만 맞아도 되고, 여럿이 맞으면 물음). 그림 번호는 `diagram-tool.py list <폴더>`의 `번호`.

> 수강생이 만든 스킬입니다(템플릿에 없음). `/portfolio-update`가 스킬 폴더·렌더러를 템플릿으로 바꾸면 사라질 수 있습니다. 사용·공유 안내: 이 폴더의 `README.md`.

## 무엇이 어디 있나

| 파일 | 역할 |
|---|---|
| `assets/diagram-tidy.js` | **다이어그램 엔진**(렌더러). 화살표를 수직·수평 직선 + 둥근 모서리로 다시 그리고(흐름도·클래스·상태·ER 그림), 원문의 `%% 격자`·`%% 화살표` 줄과 classDiagram `note for`를 처리. 같은 칸 같은 변에 붙는 화살표는 자리를 나눔. 상세 문서·발표 덱이 같이 씀 |
| 이 폴더 `diagram-tool.py` | 측정·비교 도구(파이썬 표준 라이브러리 + Chrome): `list`(문서별 그림 목록) · `measure`(겹침·크기) · `audit`(발표 덱 점검) · `compare`(전후 이미지) · `snapshot`/`diffsnap`(렌더러 고치기 전후 모든 그림 비교) · `findrepo`/`fetchrepo`(원본 코드 찾기·받기) · `env` |
| 이 폴더 `README.md` | 사람이 읽는 안내 · 설치 · 공유 |

실행: mac·리눅스 `python3 -I`, Windows `py -3 -I`(아래 `$PY`). 결과 파일은 시스템 임시 폴더 `pf-diagram/`에 생깁니다(레포 밖).

```bash
$PY -I .claude/skills/portfolio-diagram/diagram-tool.py measure 3-Arcanist CardRuntimeDeck --save <임시>/before.svg
```

`measure`의 표시 글자는 **그 그림에만 있는 칸 글자**. 결과: `shown`(페이지에 보이는 크기) · `natural`(그림 원래 크기) · `scale`(줄어든 비율, 1 미만이면 글씨가 작아 보임) · `nodes`·`labels`·`clusters`(그림 안 좌표) · `hits`(겹침 — 0건이어야 함) · `near`(글자가 칸에 6px 안으로 붙은 곳 — 답답해 보임) · `engine`(엔진이 연결됐는지).

## 지킬 원칙 (CLAUDE.md와 같음)

1. **지어내지 않는다.** 칸·선 글자·메모·설명 문장은 기술 문서에 이미 있는 사실만. 줄이거나 `<br>`로 나누는 건 되지만 새 사실을 넣지 않음.
2. **수강생 문서다.** 고치는 건 사용자가 고른 그림만. 그림 아래 설명 문장을 바꾸거나 칸을 빼는 등 **내용이 달라지는 변경은 먼저 묻고**, 배치만 바꾸는 `%%` 줄·폭·순서는 바로 해도 됨.
3. **사용자가 직접 고친 값은 덮어쓰지 않는다.** 원문을 열었을 때 내가 넣은 것과 다르면(칸 이름·`거리=` 숫자 등) 사용자가 고친 것 — 그대로 두고 알림.
4. **렌더러(`assets/`, `doc.html`, `project.html`)는 요청할 때만.** 엔진에 기능이 더 필요하면 무엇을 왜 바꾸는지 설명하고 **확인받은 뒤** 고침. 고친 뒤에는 `snapshot`/`diffsnap`으로 다른 그림이 바뀌었는지 보고, 바뀐 그림은 전후 이미지로 보여 줌.
5. **커밋은 요청할 때만**, 범위를 확인받고. 작업 트리에 다른 작업이 섞여 있을 수 있음.
6. 사용자 메모리·CLAUDE.md에 이 사람만의 다이어그램 규칙이 있으면 그것이 아래 기본 규칙보다 먼저.

## 일하는 순서

1. **훑기(요청 시):** 모든 `src/*/`(이름이 `_`로 시작하는 폴더 제외) 기술 문서의 ```` ```mermaid ```` 블록을 읽고, 아래 규칙에 비추어 개선 후보를 **우선순위 목록으로만** 보여 줌 — 각 항목에 문제·방향 한두 줄. 시퀀스 다이어그램은 제외. 고치는 건 사용자가 고른 뒤.
2. **그림 고르기:** 스크린샷이면 칸 글자로 원문 블록을 찾음. 덱에도 쓰이는 그림인지(`data/projects/<폴더>.json`에 `"kind": "mermaid"`) 확인.
3. **수정 전 캡처:** `measure … --save <임시>/before.svg`.
4. **종류 가리기:** 흐름 그림(게임 진행·처리 순서)인지 구조 그림(클래스 종속성)인지 → 칸 이름 방식이 달라짐(아래). 애매하면 물음.
   그림에 필요한 관계가 문서에 없거나 애매하면 → 아래 「정보가 부족할 때」.
5. **규칙 적용**(아래 「배치 규칙」) → `measure`로 `hits` 0건·`near` 확인 → 필요하면 `거리=`·`<br>`·폭 숫자를 고쳐 다시 잼(폭 숫자는 글꼴에 따라 다르므로 꼭 실제 페이지에서 잰 값으로).
6. **비교 이미지:** `compare <임시>/before.svg <임시>/after.svg <임시>/<이름>.png` (세로로 긴 그림은 `--vertical`) → 직접 열어 확인한 뒤 사용자에게 보냄. 사용자에게 보이는 이름·경로는 전체 경로로.
7. **발표 덱:** 덱에 쓰이는 그림이면 `audit <폴더>`. `visual-changed`·`visual-missing`은 원문이 바뀌어 생기는 것이라 `/portfolio-build <폴더>`로 풀림 — 사용자가 "나중에 한꺼번에"라고 하면 빌드할 폴더 목록만 기억해 두고 알림.
8. **마무리 보고:** 바꾼 `%%` 줄을 코드 블록으로, 겹침·크기 변화 숫자, 덱 상태, 커밋 안 함.

> **같은 파일을 에디터(Rider·VS Code)에서 열어 두면** 에디터가 들고 있던 예전 내용으로 저장되며 내 수정이 사라질 수 있습니다. 원문이 예상과 다르면 먼저 확인하고, 사용자가 에디터에서 고친 부분은 살린 채 다시 적용한 뒤 "에디터에서 파일을 다시 불러와 주세요"라고 알립니다.

## 여러 그림을 한 번에 (`전체` · `<폴더>`)

1. `list [폴더]`로 차례를 만들고, 그림이 몇 개인지·어떤 순서로 할지 한 줄로 알린 뒤 시작합니다(묻지 않고 시작해도 됨 — 배치만 바꾸는 일).
2. 그림마다 위 「일하는 순서」 3~6을 합니다. 단, **이미 규칙에 맞는 그림은 건드리지 않고** "그대로 둠 — 이유"만 적습니다(시퀀스 다이어그램은 늘 그대로).
3. **배치만 바꾸는 변경**(`%%` 줄·`<br>`·폭·순서·`direction`)은 바로 하고, **내용이 달라지는 변경**(칸 이름을 한국어로·칸 빼기·선 글자 줄이기·설명 문장 고치기·그림 옮기기)은 하지 않고 「확인할 것」 목록에 모아 맨 끝에 한꺼번에 물음 — 고른 것만 이어서 적용.
4. 그림 하나를 끝낼 때마다 짧게 진행 상황을 알리고(예: "3/9 — §3.2 카드 순환: 세로로, 겹침 0"), 비교 이미지는 그림마다 만들어 두되 보내는 건 **바뀐 그림만, 프로젝트별로 묶어서**.
5. 프로젝트 하나가 끝나면 `audit <폴더>`. 렌더러를 고쳐야만 풀리는 그림은 그 자리에서 멈추지 말고 「확인할 것」에 넣고 다음 그림으로.
6. 마지막 보고: 프로젝트별 표(그림 · 한 일 · 겹침 · 크기 변화) + 「확인할 것」 목록 + 빌드가 필요한 폴더 + 커밋 안 함.

> 그림이 많으면(10개 넘게) 프로젝트 하나씩 끝내고 보고한 뒤 다음으로 넘어가도 되는지 물어도 좋습니다. 같은 파일을 두 곳에서 동시에 고치지 않도록 하위 에이전트에 나눠 맡기지 않습니다.

## 정보가 부족할 때 (원본 코드에서 보충)

그림에 넣어야 할 관계(누가 누구를 부르는지, 상태가 무엇으로 바뀌는지, 어떤 클래스가 어떤 데이터를 갖는지)가 **기술 문서에 없거나 애매하면** 지어내지 말고 아래 순서로 찾습니다. 앞에서 찾으면 뒤는 하지 않습니다.

1. **이 레포 안:** `src/<폴더>/code/`의 `.cs` → `src/<폴더>/_intake/`(재료집·발표자료, 기술 문서가 아니라 참고만).
2. **같은 PC의 원본 저장소:** `findrepo <폴더>` — 기술 문서의 GitHub 주소와 원격 주소가 같은 저장소, 그리고 문서가 말한 소스 파일 이름(`HitBox.cs` 등)이 많이 들어 있는 저장소를 후보로 줌. 원격 주소는 포크·이름 변경으로 어긋나 있는 일이 많으므로 **`맞은 파일` 수가 가장 큰 후보**를 먼저 보고, 애매하면 사용자에게 어느 것인지 물음. 그 저장소는 **읽기만** 합니다(브랜치 전환·pull·수정 금지).
3. **원격 저장소:** 같은 PC에 없으면 문서의 GitHub 주소로 `fetchrepo <주소>` — 시스템 임시 폴더에 얕게 받아(공개 저장소, 비공개면 `gh` 로그인이 있을 때만) 읽습니다. 이 레포 안에 받지 않습니다.
4. **그래도 없으면** 어쩔 수 없음 — 그 관계는 그림에 넣지 않고(또는 기존 그대로 두고) 보고에 "근거를 찾지 못해 비워 둠: …"으로 적습니다.

코드에서 찾은 사실을 그림에 넣는 것은 **기술 문서 내용이 늘어나는 변경**입니다. 반드시 근거(`저장소/경로/파일.cs:줄`)와 함께 보여 주고 확인받은 뒤 넣습니다. 칸·선 글자는 코드에 실제로 있는 이름·호출만 쓰고, 그림 아래 설명 문장에 새 사실을 덧붙여야 하면 문장도 함께 보여 줍니다. 원본 저장소의 코드를 이 레포에 복사하지 않습니다(필요하면 `/portfolio-intake`를 안내).

## 배치 규칙

### 1. 한 방향으로 읽히게
- **줄기 하나를 일자로.** 주된 흐름(시작 → 끝)이 세로(또는 가로) 한 줄로 곧게 이어지게. 처음 읽는 사람의 눈이 따라갈 길이 하나.
- **모든 화살표는 위→아래(같은 줄 안에서는 왼→오른).** 거꾸로 가는 선은 **되돌이 하나만**, 그림 바깥쪽으로 돌려(`%% 화살표 A -> B: 나감=오른쪽 들어감=오른쪽`) "이것만 되돌아간다"가 보이게.
- **격자로 직선을 만들다 방향이 뒤섞이면 방향이 먼저.** 칸이 많고 순환이 있는 그림을 바둑판에 끼우면 화살표가 사방을 향해 오히려 안 읽힘 — 층(위에서 아래)을 먼저 정하고 그 안에서 직선을 찾음.
- **ㄹ자(두 번 꺾임)를 없애려면 받는 칸을 보내는 칸 바로 아래·옆 같은 열·줄에.** 꺾임은 한 번(ㄴ자)까지.
- **단계는 묶음(subgraph)으로**, 단계 사이 전환은 칸 대신 화살표 글자로(`A -->|씬 전환| B`). 묶음 안은 `direction LR`로 "입력 → 처리 → 결과".
- 화살표는 모두 칸이나 묶음 테두리에 닿게(허공에서 시작·끝 금지).

### 2. 격자 배치 (`%% 격자: A B | C D`)
- 칸 수가 적거나 층이 분명한 그림에. 줄은 `|`, 빈자리는 `-`, 칸 이름은 원문 id(상태 그림 시작 점은 `root_start`, 끝 점은 `root_end`).
- 이어진 칸끼리 같은 줄·같은 열에 두면 직선. 세 칸이 서로 이어진 삼각형이면 대각선 하나는 꺾일 수밖에 없음 — 미리 설명.
- **여러 열에 걸치는 칸:** 한 줄에 같은 이름을 이어 적으면(`Player Player Player`) 그 칸이 그 열들에 걸쳐 놓이고, 네모 칸이면 걸친 폭만큼 길게 늘어남. 여러 묶음이 함께 쓰는 칸을 묶음들 아래(또는 위)에 길게 깔 때 — 각 묶음의 칸과는 그 칸 열에서 곧게 오르내림. 걸친 칸으로 가는 선이 같은 묶음의 다른 칸을 지나지 않게, 묶음 안에서 그 선을 내는 칸이 맨 아래(위)에 오게 배치.
- **여러 줄에 걸치는 칸:** 같은 열에 같은 이름을 여러 줄 이어 적으면(`Idle - A | Idle - B | Idle - C`) 그 칸이 그 줄들의 가운데에 놓이고, 그 칸과 잇는 선은 상대 칸 높이에서 가로 직선. 칸의 키는 엔진이 늘이지 않으므로 이름에 `<div style=height:392px;line-height:392px>대기</div>`로 정함(`measure`로 위·아래 칸 끝에 맞춤). 여러 칸이 돌아오는 쉬는 상태를 옆에 길게 세울 때. 걸친 칸과 잇는 선이 다른 칸에 막히면 빈 줄(`Idle - -`)을 넣어 꺾을 자리를 만듦.
- **격자에서 빼기:** `%% 격자 밖: A`(격자 줄에는 적지 않음) — A를 열·줄 너비 계산에서 빼고, 이어진 격자 칸 옆에 선 글자 폭 + 32px만큼 띄워 붙임. 방향은 그 두 칸의 `%% 화살표` 줄의 격자 칸 쪽 변(나감·들어감), 없으면 오른쪽. 끝 칸(그리지 않음 등) 하나 때문에 열이 생겨 가운데 줄기가 한쪽으로 밀릴 때. 옆 칸과 겹치지 않는지는 눈으로 확인.
- `%% 격자 맞춤: 아래`(또는 `위`): 같은 줄 칸들의 아랫변(윗변)을 맞춤(가운데 대신). 키가 다른 표가 한 줄에 놓이는 ER 그림은 `위`가 가지런함. 키 큰 칸의 위 자리에서 `자리=위` 선을 내보내고 옆 칸과 오가는 선은 아래쪽에 둘 때 — 키 큰 칸 아래 빈 공간이 없어짐.
- 같은 줄 맞춤: 흐름도·상태 그림은 가운데, 클래스 그림은 윗변(칸 위 메모 자리). 같은 열은 늘 가운데. 열·줄 간격은 사이마다 선 글자 크기만큼 엔진이 정함.
- 묶음과 함께 써도 됨: 엔진이 테두리를 다시 맞추고, 같은 줄에서 시작하는 묶음은 윗변을 맞추고, 묶음 밖으로 도는 선이 있으면 테두리를 넓힘. 묶음끼리 잇는 화살표(`그룹A --> 그룹B`)는 격자가 다시 그리지 못하므로 칸끼리 이음.
- 서버·클라이언트 구조는 클라이언트 왼쪽, 서버 오른쪽.
- 시퀀스 다이어그램, 칸이 많아 격자가 오히려 복잡한 그림에는 억지로 쓰지 않음.
- **시퀀스 다이어그램:** 배치(격자·화살표)는 쓰지 않지만 엔진이 두 가지를 함 — alt·opt·loop·else 구간 이름 아래 Mermaid가 남기는 빈 줄을 줄여 첫 항목과 14px로(모든 시퀀스 그림, Mermaid 설정값으로는 안 줄어듦) · `%% 글자 자리: <메시지 글자> = <참여자A> <참여자B>`(참여자 id)로 긴 화살표의 글자를 두 세로선 사이 가운데에 두고, 사이가 글자 폭 + 양쪽 12px보다 좁으면 B 칸부터 오른쪽을 밀어 넓힘. 참여자 사이 전체 간격은 `%%{init: {"sequence": {"actorMargin": 80}}}%%`, 긴 참여자 이름은 `<br/>`로 두 줄. 상태 그림 화살표 글자의 쌍점은 `#58;`로(그냥 쓰면 그림이 깨짐).
- **ER 그림(erDiagram)도 격자·화살표 지목을 씀.** 칸 이름은 엔터티 이름(`TerrainTileDTO`), 화살표는 관계 줄의 왼쪽 → 오른쪽 엔터티. ER은 선 끝 관계 기호(까마귀발)가 넓어서 엔진이 칸 사이와 같은 변 자리 간격을 더 벌림. 같은 변에 두 선이 들어와 글자가 옆 선에 걸치면 한쪽을 `자리=오른쪽`처럼 끝으로 옮김. 격자 없이도 관계 줄 순서만 바꾸면 Mermaid가 표 자리를 다르게 놓으니, 먼저 엇갈림이 없는 순서를 찾고 `%%{init: {"er": {"nodeSpacing": 40, "rankSpacing": 50}}}%%`로 폭을 줄임.

### 3. 화살표 하나 지목 (`%% 화살표 보내는칸 -> 받는칸: …`)
- `나감=`·`들어감=` 위/아래/왼쪽/오른쪽(그 변 가운데로), `거리=N`(바깥으로 도는 줄을 칸에서 몇 px), `곡선`(그 화살표만 Mermaid 곡선). `글자=세로`(또는 `가로`): 선 글자를 그 방향 토막 중 가장 긴 곳의 가운데에(기본은 모든 토막 중 가장 긴 곳 — 꺾인 선의 글자가 원치 않는 가로·세로 토막에 갈 때). 그림 전체를 곡선으로: `%% 화살표: 곡선`. 영어 키도 됨(`out= in= gap= curve`).
- `자리=위`(아래·왼쪽·오른쪽 = 그 끝에서 14px, 숫자 = 변 시작에서 몇 px): 나가는 변의 어디서 나갈지. 받는 변이 그 높이(폭)를 덮으면 곧게 이음 — 키를 키운 칸의 위 자리에서 내보내 옆 칸 위로 지나가게 할 때(예: `%% 화살표 Held -> Idle: 나감=왼쪽 들어감=오른쪽 자리=위`, 글자가 옆 칸에 붙으면 보내는 칸의 키를 더 키움).
- 나감·들어감이 같은 변이면 바깥으로 돌아가고 그 줄 가운데에 글자를 둠. `거리`를 안 적으면 글자가 다른 글자·칸과 6px 떨어질 때까지 자동으로 벌림 — 그래도 **붙어 보이면 `거리=`를 키움**(사용자는 "너무 붙어 보인다"에 민감함).
- 되돌아가는 화살표는 받는 칸의 아래 변으로(`나감=왼쪽 들어감=아래`)도 가능.
- 엔진이 자동으로: 두 칸이 위아래·좌우로 겹치는 폭이 있으면 한 줄 직선 먼저 · 같은 두 칸을 오가는 화살표 2개는 나란한 두 줄(글자는 각자 바깥쪽) · 같은 변에서 엇갈리는 두 화살표는 자리 맞바꿈 · **같은 칸 같은 변 한 점에 화살표가 둘 이상이면 변을 따라 자리를 나눔**(위로 가는 선이 위 자리) · **선 글자는 가장 긴 곧은 토막의 가운데**(곧은 선이면 한가운데)에 두고, 칸(6px)·묶음 테두리·다른 선·먼저 놓은 글자와 겹칠 때만 같은 선을 따라 가장 가까운 빈 자리로 조금 옮김(오가는 짝·같은 변 되돌이 글자는 정해 둔 바깥쪽 자리) · **묶음 사이를 가로로 건너는 직선의 글자는 두 묶음 테두리(한쪽 칸이 묶음 밖이면 그 칸 변) 사이 빈 곳의 정가운데**, 그 열 간격은 글자 폭 + 56px(묶음 여백 16 + 글자 앞뒤 12씩)으로 좁힘 · ER 그림은 선 끝 관계 기호(약 28px)도 피하고 위아래 칸 사이를 글자 높이 + 64px 이상 벌림. 같은 변에서 나란히 나가는 선(기본 40px 간격) 중 곧은 세로선의 글자가 옆 선의 세로 토막과 같은 높이면 그 간격을 글자 폭의 반 + 12px로 벌리고, 그 칸의 위·아래 변을 같은 간격으로 맞춤.

### 4. 칸과 글자
- **칸 이름:** 흐름 그림은 한국어 "동작"(클래스명 대신), 구조 그림은 클래스명 그대로. 상태 그림의 상태도 코드에 그 이름의 enum이 없으면 한국어로 풀어 씀(`state "풀에서 대기" as InPool` — id는 그대로 두면 `%%` 줄을 안 고쳐도 됨).
- **판단 칸(마름모)은 문장으로 묻기**("플레이어 B 옆에 공간이 있는가"), 갈래는 예/아니오. "빈 칸?"처럼 명사 + 물음표 금지. 단 사용자가 기존 문구 유지를 원하면 그대로.
- **여러 주체**는 "A·B" 대신 "플레이어 A·플레이어 B"로, 이름에 글자 배경색을 달리(`<span style='background:rgba(240,150,60,.45);border-radius:4px;padding:0 4px'>플레이어 A</span>`, B는 `rgba(80,150,255,.45)`).
- **선에 메모 붙이기:** Mermaid 메모(`note right of`)는 칸에만 붙음 → 선에서 일어나는 일(그 순간 저장 등)은 `%% 선 메모: A -> B: 글<br>글`로 그 선 글자 옆(기본 오른쪽, `%% 선 메모 왼쪽: …`이면 왼쪽)에 메모 칸 모양 상자를 띄움(점선 연결, 그림에 메모 칸이 있으면 그 열에 맞추고 위 메모와 12px 띄움, 격자 줄 간격도 상자 높이만큼 벌림). 칸에 붙는 메모는 "그 상태에서 참인 것", 선 메모는 "그 전환 때 일어나는 것"으로 나눔.
- **선 글자를 한 줄로:** Mermaid는 상태 그림 등의 선 글자를 200px에서 접고 원문 HTML을 지움 → `%% 선 글자: 한 줄`(그 그림의 선 글자를 한 줄로 폄, `<br>`은 그대로). 글자가 선을 거의 덮으면 칸을 넓히지 말고 `%% 격자 열 간격: 120`(열 사이 최소 간격 px)으로 선을 길게.
- **긴 이름·긴 선 글자는 `<br>`로 나눔**(글 내용은 그대로) → 그림 폭이 줄어 페이지에서 글씨가 커짐(`scale`이 1에 가까워짐). 칸 안쪽 여백은 `%%{init: {"flowchart": {"padding": 8}}}%%`.
- **선 글자를 짧게**는 원문 뜻이 유지될 때만, 후보를 보여 주고 고르게(예: "유효한 탈출 위치 발견" → "탈출 위치 발견"/"탈출 가능"). 반대쪽 갈래와 짝이 맞으면 좋음.
- **데이터 원기둥 칸 `[(…)]`은 다른 칸에 합치지 않음.** 같은 클래스가 두 칸으로 나뉜 것은 합쳐도 됨.
- **처음 읽는 사람용 그림(개요·Why)에는 구현 메모를 넣지 않음.** 게임 장면만 쉬운 말로, 문제→해결은 그림 아래 한 줄 목록으로.
- **그 그림의 주제에 필요한 칸만.** 다른 절이 따로 설명하는 부분(예: 전투 그림 안의 저장·복원 칸)은 빼자고 제안(빼는 건 확인받고).

### 5. 폭·정렬 맞추기
- **줄기에 가운데 칸 맞추기:** 묶음 안 양옆 칸 이름을 같은 폭으로 `<div style=width:180px>이름` (따옴표·닫는 태그 없이 써도 됨).
- **묶음 폭 맞추기:** 좁은 묶음의 이름에 폭 `subgraph X["<div style=width:705px>이름"]` — 안의 칸은 가운데 그대로, 좌우 여백만 늘어남. 보이지 않는 빈칸 칸(spacer)은 쓰지 않음.
- **한 칸에서 여러 칸으로 수직으로 내리기:** 위 칸을 아래 칸들 전체 폭만큼 넓힘(`state "<div style=width:367px>Idle</div>" as Idle`) → 엔진이 각 화살표를 꺾지 않은 세로선으로. 폭은 `measure`의 `nodes`에서 아래 칸들의 왼쪽 끝~오른쪽 끝을 재서 (그 폭 − 칸 안쪽 여백 약 16px).
- 묶음 이름 아래 여백: `%%{init: {"flowchart": {"subGraphTitleMargin": {"top": 0, "bottom": 10}}}}%%`.
- 같은 줄에 나란히 둘 칸끼리는 `~~~`(보이지 않는 연결). 묶음 밖에서 안쪽 칸으로 직접 이으면 `direction LR`이 풀리므로 묶음 id로 잇기.
- 묶음 안 칸이 다른 묶음·바깥 칸과 이어지면 Mermaid가 칸을 밖으로 빼는 일이 있음 → 바깥과 이어지는 칸은 묶음에 넣지 않음.
- **묶음에는 스타일을 넣지 않음**(점선·색 없이 Mermaid 기본 모양). 시퀀스 다이어그램 `alt`·`opt`·`loop` 상자의 점선은 Mermaid 기본(조건 구간 표시)이라 그대로.

### 6. 시작 점·끝 점 (상태·흐름 그림)
판단 질문: **"맨 처음 상태가 칸으로 그릴 만큼 이 그림의 주제인가?"**
- 처음 칸이 곧 쉬는 상태이고 그리로 돌아오는 순환 → 점 빼기, 맨 위 칸이 시작(같은 문서의 다른 그림과 맞춤).
- 이 시스템 밖의 평소 상태에서 들어왔다 돌아감 → 시작 점·끝 점(◉)이 그 상태를 대신하고, 그림 아래에 "맨 아래의 끝 점은 다시 평소 상태로 돌아감을 뜻합니다." (Mermaid는 시작 점으로 들어오는 화살표를 못 그림)
- 정말 끝남(사망·파괴) → 그 갈래에만 끝 점.
- 같은 상태를 두 번 그리는 "(복귀)" 칸은 이 기준으로 줄이되, 아래 칸으로 모이는 수직 화살표가 더 읽기 좋으면(사용자가 원하면) 넓은 "(복귀)" 칸을 아래에 둠.

### 7. 그림 설명 문장
- 그림에 부가 설명을 붙일 때는 **그림 바로 아래**에 **"이 다이어그램은 ~ 도식화한 것입니다."**로 시작. "아래는…"·"아래 그림은…"처럼 그림 위에 두지 않음(발표 덱에서는 위치가 달라질 수 있음). 점·"(복귀)" 같은 표기 설명은 그 뒤에.
- 내용은 절 제목·본문에 있는 말로만. 설명이 없던 그림에 새로 지어 넣지 않음(필요하면 물음). 클래스 이름은 백틱.
- 그림을 다른 절로 옮기면 "위 전투 판정의" 같은 위치 말을 "§2의"처럼 바꿈. 절이 사라지거나 그림 종류(`flowchart LR`→`TB`)가 바뀌면 덱에 빨간 띠가 생기므로 빌드할 폴더로 기억.
